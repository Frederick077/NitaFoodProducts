# Implementation report

Scope: existing NITA FOOD PRODUCTS application in C:\NitaFoodProducts-main. Existing stack retained. No database migrations or destructive operations were executed. Cloudinary, hero, gallery, factory, production and certification image-management code was not changed.

1. **Product name editing root cause:** the controlled name input and submit payload already carried the edited name. The Prisma wrapper swallowed database failures and reported successful in-memory writes, which disappear on process restart. It also checked DATABASE_URL without loading .env. The wrapper now loads dotenv, propagates configured-database product errors, and requires PostgreSQL for product creates/updates. Admin now reports failed saves instead of silently doing nothing. These are code-confirmed failure paths; no live database reproduction was possible without DATABASE_URL.
2. **Variant editing root cause:** one size input called two state updates from the same stale array; the second update overwrote the first. The form also omitted IDs, while the server deleted/recreated every variant. Name and size now have separate inputs, functional updates, and IDs in the payload.
3. **Product Prisma queries:** inspected public/admin/detail/create/update paths. Existing wrapper reads already included both relations; create/update responses now also return images ordered by position and variants ordered by price. Admin fetches its authenticated product endpoint. Checkout queries PostgreSQL directly with variants and ordered images. Analytics uses stored order totals instead of current product prices.
4. **Relations included:** public/admin product reads and create/update responses include images and variants. Checkout explicitly loads the relations it needs. No global blanket changes to unrelated image queries.
5. **Variant IDs:** nested update by existing ID, create only without ID, reject foreign/duplicate IDs, archive omitted existing variants by setting available=false. No variant deletion occurs during product edits, including variants linked to historical orders. Archived rows remain available for admin inspection/reactivation.
6. **Cart architecture:** lightweight React CartContext plus pure cart-state functions, shared above the router; addItem/removeItem/updateQuantity/clearCart/cartItems/itemCount/subtotal. A /cart page provides item rows and checkout. Navbar cart badge uses total quantity.
7. **Persistence:** localStorage key nita-cart-v1, restored with basic shape validation. Blocked or malformed storage does not crash the cart. Browser prices remain display estimates only.
8. **Cart files created:** src/context/CartContext.tsx, src/context/cartState.ts, src/pages/Cart.tsx. App.tsx and Navbar.tsx wire them in. Existing OrderModal.tsx now selects variants/quantities and adds to the same cart; it no longer creates single-product orders.
9. **ProductDetails changes:** src/pages/ProductDetails.tsx uses selected variant and quantity, Add to Cart feedback, availability/stock validation, and resets selection state between products. ProductCard.tsx now displays variant names as well as sizes.
10. **Order schema:** retained existing customer fields, ID, timestamps, status, quantity and size; legacy productId is nullable. Added orderNumber, optional address, Decimal subtotal/total, and items relation. New order numbers use a NITA-prefixed UUID.
11. **OrderItem:** new model with orderId, optional productId/variantId, quantity, image URL, snapshot strings and Decimal money; indexes on relation fields. Product and variant references can become null without losing snapshots.
12. **Snapshots:** productName, variantName (name plus size), imageUrl, unitPrice and subtotal are stored on each item. Admin details never use current product/variant names or prices to render these items.
13. **Legacy migration:** additive migration includes one item per legacy order and preserves legacy fields/dates/status. Order number preserves the old ID. Names/images are captured as of migration; original historical names cannot be reconstructed. The old schema stored no order price, so legacy money stays NULL and is displayed as unknown instead of inventing a price.
14. **Order creation:** POST /api/orders accepts customer fields and items containing productId, variantId and quantity.
15. **Validation/pricing:** positive integer quantities, duplicate-line aggregation, product/variant existence and ownership, product/variant availability, stock, current PostgreSQL price; Decimal unit rounding, multiplication and addition. Ignores client prices/totals. A serializable Prisma transaction creates all items and their order atomically. No new stock deduction rule, fees, tax, discounts or payments.
16. **Admin details endpoint:** GET /api/admin/orders/:id behind existing requireAuth; complete JSON with items. Order list and status updates also require auth and use PostgreSQL directly.
17. **Admin UI:** src/pages/AdminDashboard.tsx modified; src/components/admin/OrderDetails.tsx created. List shows order reference, customer, phone, date, line count, total and status; clicking the reference opens full customer/item/summary details. Errors loading orders are visible.
18. **One checkout/one order:** implemented with one nested Order.create containing all OrderItems. Automated test verifies one write with multiple items; live DB atomicity/rollback acceptance remains to be run.
19. **Same product + same variant:** merges and increments quantity; automated test passes.
20. **Different variants:** remain separate cart rows; automated test passes.
21. **Rename-safe history:** snapshots are copied at checkout and displayed directly; automated snapshot test passes. Live create/rename/reopen acceptance remains to be run.
22. **Exact migration command:** npx prisma migrate deploy. For an existing matching database with no migration history, first run npx prisma migrate resolve --applied 20260905000000_baseline AFTER the schema comparison described in prisma/ORDER_MIGRATION.md. Never mark a mismatching schema as applied.
23. **Separate backfill:** not required; backfill is included in the same transaction as the additive migration. Baseline setup is required only as described in the deployment guide.
24. **TypeScript/lint:** npm run lint passed.
25. **Build:** npm run build passed; production frontend and Express bundle generated. Prisma Client generation passed. package-lock.json was repaired using npm install because npm ci found it out of sync with package.json. No new runtime dependency was added.
26. **Remaining limitations:** no .env or process DATABASE_URL is configured; no real PostgreSQL or browser acceptance tests were run. Five automated tests pass using pure state functions and a transaction double. Legacy amounts are unknowable from the old schema. Prisma emits an existing package.json configuration deprecation warning. Preview product reads remain available without a database; product writes and checkout correctly fail rather than pretending to persist.
